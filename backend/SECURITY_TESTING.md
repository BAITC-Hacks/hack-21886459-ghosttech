# Проверка безопасности

Из корня репозитория после `make setup`:

```sh
make security-check
```

Это 18 проверок реального FastAPI-приложения `app.main` через ASGI TestClient.
Каждый запуск создаёт временную SQLite-базу, применяет миграции и заполняет
её отдельными тестовыми задачами, командой и откликом. Рабочая база сайта
и текущий сервер не используются. Платный провайдер ИИ заменён заглушкой;
настоящий ключ не нужен, внешние вызовы ИИ не выполняются.

Сохранить результаты в JSON:

```sh
uv run --directory backend --locked python security_check.py --output /tmp/ghosttech-security.json
```

Проверяются права на изменение задач, команд, откликов и баллов; чтение
черновиков; CORS и обработка POST с посторонним Origin и простым `text/plain`;
доступ к операциям ИИ без аккаунта; выдача служебных файлов; SQL-инъекции
в поиске; опасные URL; подмена полей; валидация ввода; повторное начисление
баллов; защитные заголовки. Для POST/PATCH/PUT API требуется JSON, кроме
выхода без тела. Middleware проверяет `Origin` у изменяющих запросов. Cookie-сессия,
права владельца и роли проверяются сервером.

Статусы: `PASS` — проверяемое ограничение сработало; `FAIL` — не сработало;
`WARN` — отсутствует дополнительная защита; `ERROR` — проверку выполнить
не удалось. Коды выхода: `0` — нет замечаний, `1` — найдены FAIL/WARN,
`2` — ошибка выполнения. Упавшие проверки не означают поломку тестировщика.

На текущей локальной версии все **18 проверок завершились PASS**. Тестировщик
регистрирует в отдельной временной базе бизнес- и студенческий аккаунты,
создаёт их задачу, команду и отклик, а затем проверяет также разрешённые
действия владельцев. Посетитель без входа может смотреть опубликованный
каталог и демо-данные, но не изменять их. Чужие черновики и приватные
отклики не выдаются; демо-профили и демо-объекты доступны для просмотра.
Ограничение ИИ — 20 обращений на бизнес-аккаунт в сутки по UTC, меняется
через `AI_DAILY_LIMIT`; его отдельные тесты находятся в наборе `make test`.

Для cookie-входа открывайте сайт на том же origin FastAPI, например
`http://127.0.0.1:8001/`. Фронтенд на `8080` возможен при совпадающем имени
хоста, явном разрешении адреса в `FRONTEND_ORIGINS` и запросах с
`credentials: 'include'` (клиент уже использует этот режим). Сам по себе
успешный прогон тестировщика не означает готовности сервиса к публичному
размещению.

Для ручной проверки сохранённого XSS в настоящем интерфейсе:

```sh
uv run --directory backend --locked python security_check.py --serve 8011
```

Откройте http://127.0.0.1:8011/ в отдельной вкладке. Это отдельная временная
база. В названиях, карточке и отклике хранится безвредный HTML-маркер.
Проверьте каталог, карточку, рейтинг команд и бизнес-отклики: строка с
`<svg onload=...>` должна отображаться текстом, а атрибут
`data-security-xss` на элементе `<html>` не должен появляться.
Остановите сервер через Ctrl+C — временная база будет удалена.

Проверка не является полной гарантией безопасности. Она не охватывает
TLS, конфигурацию будущего reverse proxy, нагрузочные атаки, все варианты
XSS/SQL-инъекций и поведение реальной языковой модели. Браузерная проверка
и поиск известных уязвимостей зависимостей выполняются отдельно.
